# Reviewed exact purchase compatibility

`sign-purchase-compatibility.yml` signs only one manually reviewed exact
initial-page financial snapshot under the existing purchase-compatibility-v1
prerelease. Publish the1.0.0 installer first: older strict clients cannot parse
extended vectors. This workflow never changes the installer, latest or a tag.

The dispatcher must complete the source, financial-binding, initialization and
dynamic-import-scope review before dispatch. Capture hashes alone are not an
approval. An exact vector is finite known-byte approval, not an automatic graph
policy or a claim to cover arbitrary dynamic navigation. Uncertain financial
dependencies remain blocked; signed metadata does not authorize account Start.

The standalone helper is SHA256-pinned in both jobs. The first job has no signing
environment or key. Only the protected release-signing environment supplies the
original encrypted Ed25519 key and passphrase to the publishing step. Do not
retrieve, rotate, log or put those values into inputs or source. The existing
installer signer is unchanged.

Inputs pin exact raw UTF8 payload, previous signed document and review bytes by
SHA256, with base64 JSON supplied through environment variables. The review binds
the source commit, complete ordered added vector and separate evidence hashes
for exact financial behavior, dynamic noninterference within the direct initial
page scope, and off-path behavior changes. It does not assert global equivalence.

The helper permits exactly one added4..128-module vector. It preserves all
approved legacy vectors, graphPolicies and the original expiry. It rejects
rollback, changed existing pins, a three-pin shortcut and an unrelated key.
The new installer verifies all selected pins before granting contract evidence.

Publication verifies API and anonymous readback before switching asset names.
The existing compatibility.json is archived by rename; the verified candidate
is then renamed into its canonical place. GitHub has no atomic two-name swap.
A partial failure never retries mutation or reports success: inspect the actual
IDs, bytes, signatures and run stage before recovery. Only final public reads
retry on CDN propagation. Old metadata remains archived and installer latest
must remain unchanged throughout.

Run `node --test tools/sign-purchase-compatibility.test.mjs` after changes.
Updating helper code also requires updating both workflow hash pins. Tests use
disposable generated keys and mocked network responses, never the production key.
